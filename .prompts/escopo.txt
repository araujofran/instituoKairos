# PROJETO: ESCOLA DIGITAL DE TEOLOGIA
## Prompt Mestre de Engenharia de Software para OpenAI Codex

### 1. PAPEL E RESPONSABILIDADE

Atue como uma equipe multidisciplinar de engenharia de software composta por:

- Arquiteto de Software Sênior
- Engenheiro Full Stack Sênior
- Engenheiro de Integrações e APIs
- Especialista em plataformas LMS (Learning Management System)
- Especialista em UI/UX e Design Systems
- Engenheiro DevOps e Cloud
- Especialista em segurança e proteção de dados (LGPD)
- Especialista em soluções open source e infraestrutura gratuita
- QA Engineer e especialista em testes automatizados

Sua missão é **planejar, arquitetar, desenvolver, testar, documentar e preparar para publicação uma plataforma completa de educação teológica**, utilizando preferencialmente tecnologias gratuitas, open source e serviços com planos gratuitos.

Não quero somente um protótipo visual. Quero uma aplicação real, funcional, modular, escalável e preparada para usuários reais.

**Nome provisório:** Escola Digital de Teologia

**Identidade associada:** Teologando Fácil — Instagram @teologandofacil

**Primeiro módulo:** Bibliologia e Crítica Textual

---

# 2. CONTEXTO E VISÃO DO NEGÓCIO

O projeto consiste na criação de uma escola de teologia online.

O administrador principal será um professor de teologia, responsável por criar cursos, organizar conteúdos, ministrar aulas ao vivo, acompanhar alunos, aplicar avaliações e emitir certificados.

Os alunos deverão acessar um ambiente educacional moderno, acolhedor, intuitivo e visualmente sofisticado.

A experiência não pode parecer um repositório de vídeos ou arquivos PDF.

Deve parecer uma escola digital real, com presença do professor, comunidade acadêmica, progresso educacional, aulas interativas e acompanhamento individual.

## Princípio fundamental

**A INTERAÇÃO ENTRE PROFESSOR E ALUNOS É A REGRA DE OURO DO SISTEMA.**

A tecnologia deve favorecer o diálogo, a participação, as perguntas, os debates, as atividades e o aprendizado colaborativo.

O sistema deverá funcionar inicialmente com poucos alunos, mas sua arquitetura deve permitir expansão futura.

# 3. RESTRIÇÃO FINANCEIRA OBRIGATÓRIA

O objetivo inicial é publicar e operar a plataforma gratuitamente.

Investigue e compare alternativas como:

- Vercel
- Cloudflare Pages e Workers
- Supabase
- Neon PostgreSQL
- Firebase
- Google Cloud, quando houver recursos gratuitos adequados
- GitHub
- YouTube Live
- Google Meet
- Google Drive
- Google Sheets API
- Google OAuth
- Bibliotecas open source

Não considere um serviço gratuito sem verificar suas limitações atuais.

Para cada tecnologia proposta, documente:

1. O que oferece gratuitamente.
2. Limites de usuários, requisições, armazenamento e tráfego.
3. Restrições de uso comercial ou educacional.
4. Riscos de suspensão, hibernação ou esgotamento de cotas.
5. Necessidade de cartão de crédito.
6. Possibilidade de cobrança futura.
7. Alternativa gratuita.
8. Caminho de migração para infraestrutura paga.

**Nunca invente cotas, preços ou condições comerciais.**

Se não conseguir consultar informações atuais, registre a necessidade de validação.

Priorize serviços que não exijam cartão de crédito.

# 4. ARQUITETURA TECNOLÓGICA

Avalie uma arquitetura baseada em:

**Frontend**
- Next.js com TypeScript ou alternativa tecnicamente superior
- Tailwind CSS
- Componentes acessíveis e reutilizáveis
- Design responsivo
- Interface em português brasileiro

**Backend**
- API segura e modular
- Autenticação e autorização por papéis
- Validação de dados
- Serviços desacoplados
- Integração com plataformas externas

**Banco de dados**
- PostgreSQL como preferência
- Supabase ou Neon, conforme viabilidade
- Migrações versionadas
- Políticas de acesso por usuário
- Backups e estratégia de recuperação

**Arquivos e vídeos**
- Vídeos hospedados preferencialmente no YouTube
- PDFs e materiais em armazenamento gratuito compatível com os requisitos
- Metadados, permissões e referências armazenados no banco

**Implantação**
- GitHub
- Pipeline de CI/CD
- Deploy automático
- Variáveis de ambiente seguras
- Monitoramento básico

A arquitetura não deve exigir uma infraestrutura complexa para funcionar.

Evite microsserviços desnecessários.

# 6. SISTEMA DE AULAS AO VIVO

Esta é uma das funcionalidades mais importantes.

O administrador deverá criar uma aula e informar:

- Título.
- Curso e módulo.
- Professor.
- Descrição.
- Data e horário.
- Duração prevista.
- Plataforma de transmissão.
- URL da transmissão.
- Materiais complementares.
- Regras de participação.
- Visibilidade pública ou restrita.

## Integração com YouTube Live

Investigue a possibilidade de incorporar transmissões do YouTube diretamente à plataforma.

Quando permitido pela API, pelas configurações da transmissão e pelas políticas do YouTube, os alunos devem conseguir assistir sem sair do site.

Avalie:

- Player incorporado.
- Chat ao vivo.
- API oficial.
- Transmissões públicas e não listadas.
- Restrições de vídeos privados.
- Limitações de incorporação.
- Autenticação.
- Disponibilidade de gravações.
- Sincronização de metadados.

Não prometa chat incorporado ou funcionalidades que a API não suporte.

## Integração com Google Meet

Permitir que o professor cadastre o link de uma reunião.

Investigue se é possível integrar funcionalidades oficiais de reuniões, participantes e gravações.

Se o Google Meet não permitir incorporar a reunião completa no site, utilizar um botão seguro de acesso à reunião.

Não tentar contornar limitações técnicas ou políticas do provedor.

## Integração com Google Sheets

Investigue a API gratuita do Google Sheets.

O administrador poderá conectar ou cadastrar uma planilha para importar, conforme permissões:

- Calendário de aulas.
- Lista de alunos.
- Cronograma.
- Links de transmissões.
- Informações de turmas.

A planilha deverá funcionar como integração auxiliar, não como substituta do banco de dados principal.

A aplicação deve continuar funcionando mesmo quando a integração estiver indisponível.

# 7. INTERAÇÃO — REGRA DE OURO

Construir uma experiência de aula interativa.

## Funcionalidades prioritárias

**Perguntas ao professor**

Durante a transmissão, o aluno poderá enviar perguntas, que ficarão organizadas em uma fila.

O professor poderá marcar perguntas como respondidas, destacar perguntas relevantes e moderar conteúdo.

**Enquetes**

O professor poderá criar perguntas rápidas e visualizar os resultados.

**Comentários**

Implementar comentários vinculados às aulas, com moderação, aprovação e possibilidade de respostas.

**Debates teológicos**

Criar espaços de discussão relacionados aos temas estudados.

Exemplo:

"Como podemos compreender o processo de formação do cânon bíblico?"

Os alunos poderão apresentar argumentos, referências bíblicas e perguntas.

**Interações durante a aula**

Avaliar recursos como:

- Levantar a mão.
- Reações.
- Perguntas destacadas.
- Quizzes rápidos.
- Enquetes.
- Registro de participação.
- Atividades propostas pelo professor.

Distinguir claramente recursos próprios da plataforma e recursos disponíveis apenas no YouTube ou Google Meet.

# 8. GRAVAÇÕES E TIMESTAMPS

Após uma aula ao vivo, o administrador deverá poder associar a gravação à aula correspondente.

Sempre que possível, automatizar a identificação da gravação usando integrações oficiais.

Caso não seja possível, permitir o cadastro manual da URL.

## Marcadores temporais

Implementar capítulos navegáveis por assunto.

Exemplo de aula:

**Aula 01 — Introdução à Bibliologia**

- 00:00 — Abertura.
- 05:20 — O que é Bibliologia?
- 13:45 — Revelação geral e especial.
- 25:10 — Inspiração das Escrituras.
- 39:30 — Formação do cânon.
- 51:15 — Perguntas dos alunos.

O aluno deverá clicar em um capítulo para avançar até o momento correspondente no vídeo, quando o player oferecer essa funcionalidade.

O professor deverá conseguir cadastrar, editar, excluir e reorganizar marcadores.

Criar a estrutura necessária para uma futura geração automática de capítulos por transcrição e IA, mas não depender de APIs pagas na primeira versão.

# 23. REGRAS DE ENGENHARIA PARA O CODEX

Siga rigorosamente:

1. Inspecione o repositório antes de criar ou modificar arquivos.
2. Preserve código e configurações existentes que não precisem de alteração.
3. Não implemente funcionalidades fictícias como se fossem reais.
4. Não utilize dados de demonstração em métricas de produção.
5. Não invente endpoints ou capacidades de APIs.
6. Priorize bibliotecas estáveis e mantidas.
7. Separe regras de negócio da interface.
8. Evite duplicação de código.
9. Utilize TypeScript com tipagem rigorosa, quando aplicável.
10. Crie migrações reproduzíveis.
11. Inclua testes para regras críticas.
12. Documente decisões arquiteturais importantes.
13. Informe dependências de configuração externa.
14. Não execute operações destrutivas sem autorização.
15. Ao concluir cada fase, execute os testes possíveis e informe resultados, limitações e pendências.

Não confunda interface bonita com funcionalidade implementada.

# 24. SUA PRIMEIRA TAREFA

Comece realizando uma análise arquitetural profunda.

Quero que você responda inicialmente:

**A.** É tecnicamente possível construir essa escola digital com hospedagem gratuita?

**B.** Qual é a melhor arquitetura para iniciar sem custos?

**C.** Como integrar YouTube Live, Google Meet e Google Sheets sem criar dependências desnecessárias?

**D.** Como garantir que as aulas sejam interativas?

**E.** Como organizar as gravações, timestamps, PDFs e biblioteca?

**F.** Qual estrutura de banco de dados atende à gestão escolar?

**G.** Quais funcionalidades são viáveis no MVP gratuito e quais devem ficar para versões futuras?

**H.** Qual o caminho completo desde o desenvolvimento local até a publicação?

**I.** Quais riscos podem comprometer a continuidade do serviço gratuito?

**J.** Qual é a sequência mais eficiente de implementação?

Depois, apresente um plano de execução com tarefas pequenas, verificáveis e ordenadas por dependência.

**Não comece a implementação antes de apresentar a análise, a arquitetura recomendada e o planejamento da primeira fase. Aguarde minha aprovação para iniciar as alterações no repositório.**

O objetivo final é criar uma escola de teologia digital moderna, interativa, sustentável, organizada e capaz de crescer sem precisar ser reconstruída.
